# Status File Contract

Each output node's verification results persist in a co-located, machine-written `spx.status.json` file that is the claim of the methodology version the product declares in `spx.config.yaml`. The 4.0 claim carries the node's `state`, the `malleability` it was measured against, and `verification` results grouped by type: `test`, `eval` and `probe` entries keyed by the node-relative path their tag links, `audit` entries keyed by rule slug, and `evidence` entries keyed by the kind of evidence audited. A `.product` carries no claim. A variant's claim also carries its parent's entries, keyed by tree-absolute path and produced with the selection source set to that variant, and the parent's claim carries its state derived across its variants and no results. Every entry carries its `verdict`; a passed or failed entry carries a pin of the `commit` checked out when the result was produced and the `read` paths the result depended on; an Agentic or Attested entry also carries its `actor` and `run`. The 4.0 claim stores no `overall` rollup. The version-1 claim, `schemaVersion: 1` with mechanism objects that carry `overall` rollups and bare `passed`, `failed` or `not-run` references, stays readable. The file stores only execution results that Git cannot answer; Git answers node identity, authorship and time, and compares a pinned commit with the tree over the read paths. The committed file is a claim its author publishes: `spx spec status` derives the node lifecycle state from it when present and from the tracked spec tree when absent, reports each result's verdict, pin, actor and run and whether its pin is current against the checkout, and `spx spec status --update` folds the results a recorded verification run produced into it. Neither command executes verification, and spx decides no gate from the facts it reports.

## Rationale

Per-node co-location ties recorded results to the node's own commits while Git owns identity, provenance, assertions, evidence links, source, config, and history; central status maps, copied Git facts, and top-level lifecycle-only fields lose that boundary. `spx.status.json` is the committed projection of runtime results, distinct from gitignored execution evidence under `.spx/`, and CI recomputes that projection from the checkout of every commit it checks, so forged or stale status in a checked commit cannot pass.

Separating the claim from its reproduction is what lets the status path stay a read: the author folds the evidence a run recorded, and CI, running the configured suite over a full checkout, is the authority that reproduces a passing claim and refutes one the product no longer supports. A status command that executed verification to fill a gap would re-derive per node what a run schedules in one batch, and would write a result no recorded run produced.

A pin makes a result's currency checkable without re-running it: a result is current while no path it read differs between its commit and the checkout, so an unrelated commit invalidates nothing and a change to one read path invalidates exactly the results whose pins read it, except that an Audit or evidence result stays current when spx proves that every changed pinned path is a spec and every change in it is a link-format edit, which keeps each link's label and resolved target. A read set holds the declaration, the verification artifact and the subject: the fold adds the node's spec and the linked artifact to the paths the adapter reported, a `probe` pin names the spec, the probe's directory and the implementation files the attested run observed, an `evidence` pin names the spec, the node's `tests/` or `evals/` directory and the implementation files its linked verification reached, and an `audit` pin names the spec and the subject paths its verification run records. A 4.0 claim records a passed or failed result only with its pin; a result over an uncommitted read path, from an adapter that reports none, or from a language whose runs are not journaled is recorded `not-run` with no pin. For a language whose dependencies a lockfile resolves, the lockfile is among the read paths, so a pin names the resolution the result ran under and claims nothing about the installed tree, which spx does not inspect; the runner owns the conformance of its installed dependencies to that lockfile, both when it produces a result and when it reuses a pin.

## Product properties

1. `spx.status.json` is the claim of the methodology version the product declares: the 4.0 claim carries `state`, `malleability`, and `verification` results grouped by type, with `test`, `eval` and `probe` entries keyed by the node-relative path their tag links, `audit` entries keyed by rule slug, `evidence` entries keyed by the kind of evidence audited, and a variant's copies of its parent's entries keyed by tree-absolute path; every entry carries its `verdict` of `passed`, `failed` or `not-run`, a passed or failed entry carries a pin of `commit` and `read` paths, an Agentic or Attested entry also carries `actor` and `run`, an `evidence` entry exists only on an implementation-malleable node, one per kind of linked evidence it has, and the 4.0 claim stores no `overall` rollup. A `.product` carries no claim. The version-1 claim, with `schemaVersion: 1` and mechanism objects keyed by `test`, `eval` and `audit` that carry `overall` values of `passed`, `failed`, `partial` or `not-run`, stays readable.
2. `spx spec status` derives a node's lifecycle state from committed verification results when `spx.status.json` exists and derives live structural state when it is absent. From a 4.0 claim it derives `passing` when every result the malleability requires is current and passed; `failing` otherwise when the node's claim recorded `passing` at a commit at or after the latest change to its spec or a decision record governing it, which Git answers, a deleted artifact included; `declared` when a required verification artifact is missing; and `specified` otherwise. `--update` folds the results a recorded verification run produced: a committed entry whose pin is current and whose verdict and read set equal the run's stays as committed, a reference a run covers whose evidence is stale keeps its committed entry when one exists and, with none committed, is written `not-run` with no pin, which CI regeneration over the fresh result of the configured suite replaces, a test reference no run covers is `not-run` with no pin, and a committed eval, probe, audit or evidence entry no run covers stays as committed while its pin is current and is `not-run` with no pin otherwise. `--update` writes the claim only in a run where Validate has already passed for the checkout, as CI orders it, and takes no Validate input. Neither form executes verification.
3. On every pull-request head targeting the default branch, and on every push to the default branch whose changed paths do not all lie in the instruction-document paths `CLAUDE.md`, `AGENTS.md`, `README.md`, `LICENSE`, and `docs/**`, CI runs Validate and, once it passes, the configured verification suite, regenerates the status projection for the checkout, and rejects that commit when a node's regenerated state, or an entry's regenerated verdict or read set, differs from the committed `spx.status.json`; a difference in an entry's pin commit alone does not reject the commit.

## Verification

### Testing

- ALWAYS: a generated `spx.status.json` conforms to the shape of the methodology version the product declares ([conformance])
- ALWAYS: `spx spec status` derives lifecycle state from committed verification results when `spx.status.json` exists and falls back to live structural derivation when it is absent ([mapping])
- ALWAYS: regenerating the status projection over a checkout whose committed `spx.status.json` differs from the projection of the recorded evidence rewrites that file to the projection, so the regeneration leaves `spx/` changed ([compliance])
- ALWAYS: the committed-status comparison reports a difference exactly when a node's state or an entry's verdict or read set differs between the committed and the regenerated claim, and reports none when only pin commits differ ([compliance])
- ALWAYS: a 4.0 claim records a passed or failed result exactly when its read set holds the node's spec, the verification artifact (a probe's whole directory) and a subject path, and every read path matched the checked-out commit; any other result reads `not-run` with no pin ([mapping])
- ALWAYS: a change to one pinned path marks exactly the results whose pins read it as not current, except an Audit or evidence result whose every changed pinned path is a spec changed only by link-format edits ([compliance])
- ALWAYS: a 4.0 claim derives `failing` exactly when the node's claim recorded `passing` at or after its latest declaration change and it is not now `passing`, and stays `failing` across later projections ([mapping])
- ALWAYS: an unrelated commit rewrites no pin, and regenerating the projection from the checkout reproduces every committed claim ([compliance])
- ALWAYS: a version-1 claim and a 4.0 claim are each read and reported with their shape ([mapping])

### Audit

- ALWAYS: CI runs Validate, then, once it passes, the configured verification suite, and then regenerates the status projection on every pull-request head targeting the default branch and every push to the default branch whose changed paths do not all lie in the instruction-document paths `CLAUDE.md`, `AGENTS.md`, `README.md`, `LICENSE`, and `docs/**`, and rejects the commit when a node's regenerated state or an entry's regenerated verdict or read set differs from the committed claim, never when only a pin commit differs ([audit])
- ALWAYS: write `spx.status.json` only through the `spx spec status --update` path — every other path reads ([audit])
- ALWAYS: `spx spec status --update` writes a claim only in a run where Validate has already passed for the checkout; the writer takes no Validate input and assumes no Validate result ([audit])
- ALWAYS: place each `spx.status.json` in the directory of the node it describes; node identity comes from file location, not file content ([audit])
- ALWAYS: store only results that Git cannot answer; node identity, assertion text, evidence links, test source, eval definitions, audit rules, config, authorship, and time come from Git, which also compares a pinned commit with the tree over the read paths ([audit])
- ALWAYS: fold `spx spec status --update` verification results from the evidence the configured verification surfaces recorded ([audit])
- ALWAYS: report only derivable state from `spx spec status` without `--update`: the committed verification projection when present, otherwise the live structural derivation ([audit])
- NEVER: treat a missing `spx.status.json` as an error or a fixed state; absence routes to live derivation ([audit])
- NEVER: offer `spx.status.yaml` or `spx.status.toml` — the status file is machine-written JSON only ([audit])
- NEVER: execute verification from `spx spec status` in any form, `--update` included — the status path folds recorded evidence and a verification surface produces it ([audit])
- ALWAYS: keep the committed entry, with its verdict, pin, actor and run, of an evidence reference whose pin is current and whose verdict and read set equal the recorded run's, and of one a recorded run covers whose evidence is stale — the claim stands until a run records a replacement ([audit])
- NEVER: keep a committed entry for a test reference no recorded run covers — it reads `not-run` with no pin, so the regenerated projection refutes a deterministic claim no run produces; a committed eval, probe, audit or evidence entry whose pin is current stays, because CI checks those pins and reruns only deterministic results ([audit])
- NEVER: a pin claims anything about the installed dependency tree — it names the lockfile as the resolution the result ran under, and the runner owns the conformance of its installed dependencies to that lockfile ([audit])
