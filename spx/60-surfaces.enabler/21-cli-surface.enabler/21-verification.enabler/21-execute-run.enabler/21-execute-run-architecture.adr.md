# Execute-Run Command Surface Architecture

The `spx verification <type> run [paths…]` command paths are registered by the single `spx verification` Commander descriptor of `spx/60-surfaces.enabler/21-cli-surface.enabler/21-verification.enabler`, one noun command per verification type the executor of `spx/34-verification.enabler/43-execute.enabler` can drive, each carrying a `run` verb, per `spx/14-cli-composition.adr.md`. A process-agnostic execute-run handler under `src/commands/verification-exec/` composes that executor: it resolves the verb's positional operands to test files through the operand-selection library of `spx/41-test.enabler/90-targeted-execution.enabler` under `src/lib/test-targeting/`, records one `file`-scoped run whose selector is the narrowest product-relative directory enclosing every operand — the spec-tree root when no operand is given — with the executor's request as the recorded run input, drives the type's streaming runner through the verification-type registry over production recorder operations rooted at the product root, and returns the run locator, the terminal status, and the runner outcome as one structured result. The product root is the local worktree root the effective invocation directory resolves to under `spx/15-worktree-management.pdr.md` — `git rev-parse --show-toplevel`, or the invocation directory itself outside a repository, in which case the result carries a warning — the same resolution `spx test` applies, so discovery, the selector, the recorder, and the runner share one root from any directory inside the product. The handler composes every diagnostic that embeds an operand, a path, a run identity, or a caught failure message through the terminal-text primitive of `spx/13-cli.enabler/15-cli-architecture.adr.md` and returns it as composed text, so the provenance decision is made where the value is produced, and maps `passed` to the zero exit code and every other outcome to a non-zero one. The descriptor owns Commander wiring and the process boundary: it registers the type nouns and the shared positional-operand vocabulary of `spx/29-verification-path-scope.pdr.md` from one declaration `spx test` also registers, serializes the structured result to standard output through the primitive's JSON composition, writes the warning and the diagnostic to standard error, routes the run's local event stream to standard error, applies the exit code, and renders a recorder or runner failure the handler propagates through the handler's failure diagnostic with the error exit code, so no run failure escapes as an unhandled rejection. Neither the handler nor any other `src/commands/verification-exec/` module imports Commander or writes to the process boundary.

## Rationale

The caller-driven `spx verification run <verb>` surface and the spx-driven `spx verification <type> run` surface are two shapes of one command family, so `spx/14-cli-composition.adr.md` places both on the single `verification` descriptor: the composition root registers each domain at the root program, and a second descriptor cannot attach subcommands to the first descriptor's `verification` command. The recorder/executor split therefore lives at the `commands/` layer — the record-run handlers under `src/commands/verify/` and the execute-run handler under `src/commands/verification-exec/`, both imported by the one descriptor — and the set of type nouns the descriptor registers is the executor's own runner registry, so a type gains a command path by registering a runner and the descriptor names no type of its own.

Positional operands realize the shared path-operand vocabulary of `spx/29-verification-path-scope.pdr.md`, and resolving them through the operand-selection library — a capability two command domains reach, so it lives under `src/lib/` per `spx/14-cli-composition.adr.md` rather than inside either command's domain — gives `spx verification test run` and `spx test` one meaning for a file operand, a node operand, and the recursive widening — an operand that selects no discovered test file is reported before any run opens, so a typo never records an empty run. A verification run carries one selector, while the run's coverage is the module scope the runner streams; the selector is therefore an addressing key, not the coverage claim, and the narrowest enclosing directory is the deterministic key that names what the caller asked for without inventing a scope type — the recorder's `file` scope already normalizes any safe product-relative path. Recording the executor's request as the run input keeps the run reconstructible through `spx verification run input` like a caller-driven run.

Resolving the product root from the invocation directory, rather than taking the invocation directory as the root, is what makes the command hold from a subdirectory: `spx/15-worktree-management.pdr.md` resolves tracked `spx/` content to the local worktree root, and a run rooted at a subdirectory would discover no test file, record a run whose input names no test path, and drive the runner over the wrong tree. Keeping the handler free of Commander and the process boundary lets it verify with injected discovery, product-root resolution, runner resolution, and recorder dependencies against controlled implementations, without a real Vitest run, journal I/O, or a built executable — the executor is already a pure composition over injected recorder operations and a runner resolver, so the handler composes the real executor and extends that injection to its own boundary rather than injecting the executor itself, which would invite the mocked-handler-layer verification `spx/14-cli-composition.adr.md` forbids. The handler owns the exit-code mapping and the diagnostic composition because both are decisions about the run's outcome, not about the process: the caller-driven record-run handlers likewise return an exit code and rendered output for their descriptor to apply, and `spx/13-cli.enabler/15-cli-architecture.adr.md` places composition where the authored and external segments are still distinguishable, which is the handler. The handler propagates a recorder or runner failure after the executor's best-effort seal rather than folding it into a result, because the caller-driven record-run handlers already distinguish a lifecycle failure from a recorded outcome; the descriptor is the one place that turns the propagated failure into a diagnostic and an exit code, which keeps the caught message escaped and the process from ending on an unhandled rejection. Composing diagnostics through the terminal-text primitive keeps an operand, a product path, or a run token that carries control bytes from repositioning or recoloring the caller's terminal, per `spx/13-cli.enabler/15-cli-architecture.adr.md`; the structured result on standard output is a JSON document composed through the primitive's JSON serialization, whose grammar escapes every embedded value so no raw control byte reaches the terminal while a machine consumer still decodes each value verbatim — the same composition `spx diagnose` serializes its JSON report through. A non-zero exit for a failed or interrupted run — including a product that supplies no runner, whose searched directory the result names — is what lets a CI job gate on the command, while the run remains inspectable through `spx verification run status` and `render` whatever the exit code.

## Invariants

- The execute-run handler's durable effects flow only through the injected executor and recorder operations; the handler constructs no journal event and performs no Commander or process I/O.
- The command's positional operands reach the executor as the run's selected test paths without a scope-naming flag, and an operand resolving to no discovered test file opens no run.
- Exactly one Commander descriptor registers the whole `spx verification` command family, wiring the record-run handlers of `src/commands/verify/` and the execute-run handler of `src/commands/verification-exec/`.
- The set of verification-type nouns the descriptor registers equals the set of types the executor's runner registry resolves.
- The exit code is zero exactly when the recorded terminal status is `passed`.
- Discovery, the run selector, the recorder, and the runner request share one product root: the local worktree root the effective invocation directory resolves to.
- A recorder or runner failure the handler propagates reaches the caller as a rendered diagnostic on standard error with the error exit code, never as an unhandled rejection.

## Verification

### Testing

- ALWAYS: invoked from any directory inside the product, the handler discovers, selects, records, and drives the runner against the local worktree root that directory resolves to; invoked outside a repository, it roots the run at the invocation directory and its result carries the not-in-repository warning ([compliance])
- ALWAYS: a failure the handler propagates is written by the descriptor as a terminal-composed diagnostic whose caught message is escaped, with the error exit code and nothing on standard output ([compliance])

### Audit

- ALWAYS: the execute-run handler accepts the runner resolver, test-file discovery, product-root resolution, the recorder dependencies, and the effective invocation directory through injected parameters and composes the real executor over them, so it verifies with controlled implementations without Commander, process, or journal I/O ([audit])
- ALWAYS: the recorder dependencies the handler accepts are the recorder's own dependency type minus the fields the handler and its recorder operations supply — the product root, the input reader, the payload reader, and the drive mode — so the two shapes cannot drift ([audit])
- ALWAYS: the descriptor registers the recursive modifier and the forbidden path-scope flags from the positional-operand vocabulary declaration `spx test` registers from, under `src/interfaces/cli/lib/`, so the two surfaces share one operand grammar per `spx/29-verification-path-scope.pdr.md` and `spx/60-surfaces.enabler/21-cli-surface.enabler/11-cli-surface.pdr.md` ([audit])
- ALWAYS: the single `spx verification` descriptor of `spx/14-cli-composition.adr.md` wires the execute-run handler, which lives under `src/commands/verification-exec/`, and derives its verification-type nouns from the executor's runner registry; no second descriptor attaches the verification-type command paths to the `verification` command and no descriptor constant names a verification type ([audit])
- ALWAYS: the handler resolves the command's positional operands through the operand-selection library of `spx/41-test.enabler/90-targeted-execution.enabler` under `src/lib/test-targeting/`, never through the `test` command's own domain modules, and forwards the selected files to the executor as the run's test paths per `spx/29-verification-path-scope.pdr.md`, so the command surface names no language per `spx/19-language-registration.adr.md` ([audit])
- ALWAYS: the run's selector is the `file` scope whose identity is the narrowest product-relative directory enclosing every operand, or the spec-tree root when no operand is given, and the recorded run input is the executor's request ([audit])
- ALWAYS: every diagnostic the handler composes for this command path embeds operands, paths, run identities, and caught failure messages as external segments of the terminal-text primitive and reaches the descriptor as composed text rather than a string the descriptor brands on the handler's behalf, and the descriptor writes it and the not-in-repository warning to standard error while serializing the structured result to standard output through the primitive's JSON composition ([audit])
- NEVER: a module under `src/commands/verification-exec/` imports Commander or writes to the process boundary — `process.exit`, `process.stdout`, `process.stderr`, `process.stdin` — that boundary belongs to the descriptor per `spx/14-cli-composition.adr.md` ([audit])
- NEVER: `vi.mock()`, `jest.mock()`, or module replacement substitutes for the handler's injected executor, runner resolver, discovery, or recorder operations — the handler receives controlled implementations through its public parameters ([audit])
