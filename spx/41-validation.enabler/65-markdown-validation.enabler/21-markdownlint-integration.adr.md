# Markdownlint Integration

Markdown validation uses markdownlint-cli2's programmatic Node API (`main()`) through a typed dependency seam, with configuration built in code and passed via `optionsOverride`, so no config files are written to validated directories. Link checking is supplied through the config object's `customRules` per directory: `docs/` uses the custom rule `markdownlint-rule-relative-links` with its product-root `root_path`, and `spx/` uses a product-owned link-shape rule in its place. The product rule composes `markdownlint-rule-relative-links`' link-existence and heading-fragment checks, presenting each tree-absolute `spx/` href to them as anchored at the product root, and itself reports a link with a `../` climb, a link with a leading-slash anchor, a relative link whose path enters a descendant node's directory, and a decision path written as text outside a link — bare or in an inline code span — outside fenced code blocks, each naming the file, the line, and the offending link or path. A decision path is a path that begins `spx/`, ends in `.adr.md` or `.pdr.md`, and resolves to a decision tracked in the product; neither a decision filename without the `spx/` prefix nor an `spx/` path that resolves to no tracked decision is a decision path, and neither is reported. When the product root is a git repository, the step reads the paths git tracks under `spx/` once per validation run and supplies them, with the product root, through the product rule's configuration; the product rule then resolves each admitted href to a product-relative path — a tree-absolute href from the product root, a node-local href from the citing file's directory — and reports a target inside the product root that git does not track as a broken link, naming the file, the line, and the link, and withholding it from the composed checks, and it recognizes a decision path written as text by looking the path up in the same tracked set. Outside a git repository the step supplies no tracked paths: the composed existence check alone decides whether a link resolves, and no text resolves to a tracked decision, so no decision path written as text is reported. The step in `src/validation/steps/markdown.ts` exports `validateMarkdown(options, deps)` — taking a `ValidateMarkdownOptions` that carries a `MarkdownValidationTarget[]` of directory or file targets plus an optional product root, and a `MarkdownValidationDeps` that carries the markdownlint entry point and the tracked-path listing, whose default reads `git ls-files` through the shared tracked-path reader in `src/lib/git/tracked-paths.ts` over the injected git runner — and returns a result with a success flag and structured error objects. The step also exports the pure config builder `buildMarkdownlintConfig(directoryName)` and `getDefaultDirectories(productDir)`, which returns the `spx/` and `docs/` directories that exist under the product root. Markdown is registered as a `ValidationLanguageDescriptor` (`markdownValidationLanguage`) composed into the pipeline through the validation registry `src/validation/registry.ts`, ordered after the TypeScript language, so `spx validation all` dispatches it as a registry-composed stage and never by a hardcoded step index.

## Rationale

The programmatic API avoids subprocess overhead, eliminates discovering or locating a CLI binary, and yields structured error output without parsing stdout, while configuration built in code is versioned with the source, testable as a pure function, and produces no side effects in validated directories. ESLint's Node API has different orchestration ergonomics and remains subprocess-backed, whereas markdownlint-cli2's `main()` is designed for programmatic use. Because `main()` returns only an exit code, its logged output is captured via `logMessage`/`logError` callbacks and parsed into structured error objects, and the custom relative-links rule — which ships no TypeScript types — has its object shape verified by the config builder test.

The methodology's link grammar admits only node-local and tree-absolute links inside `spx/`, so `spx/` needs a rule that both resolves tree-absolute hrefs and rejects every other shape; `markdownlint-rule-relative-links` resolves a href from the citing file's directory or, for a leading-slash href, from `root_path`, and rejects neither a climb nor a leading slash. Composing its existence and fragment checks keeps one resolution implementation for both directories while the product rule owns only the shape rules, and `docs/` uses `markdownlint-rule-relative-links` directly. Checking target existence on disk or heading fragments in the product rule is excluded because it duplicates the existence and fragment-slug logic `markdownlint-rule-relative-links` supplies; a post-pass over markdownlint's output is excluded because it reports outside markdownlint's structured error stream that the step parses.

Filesystem existence is not enough inside `spx/`, because the spec tree is the tracked tree: an uncommitted or ignored file exists in one working copy only, so a link to it passes there and breaks in every other checkout and in CI. The product rule therefore adds one tracked-membership step ahead of the composed checks. It maps an admitted href to the product-relative path the composed checks would open, solely to look that path up in the tracked set; a target absent from that set — untracked, ignored, or nonexistent — is broken by membership alone, while a tracked target's existence on disk and its heading fragments stay with `markdownlint-rule-relative-links`, so the step is a membership filter and not a second existence or fragment check. The tracked set is read once per run through the step's injected dependency and reaches the rule through markdownlint's rule configuration, the only channel into a custom rule, which keeps the rule a pure function of its configuration and token stream and keeps git out of markdownlint's per-file pass. Querying git per link from inside the rule is excluded because it spawns a subprocess per link and hides a git dependency inside markdownlint. Outside a git repository there is no tracked tree to check against, so validation falls back to existence, as product-root resolution falls back to the working directory.

A decision path written as text is a citation only when it names a decision the product holds. An example or fixture path inside an assertion has the shape of a decision path and names nothing, and a decision filename without the `spx/` prefix cannot be resolved to one decision, because numeric prefixes repeat across directories; reporting either would turn data into a defect. The tracked set that reaches the rule decides the question by membership, so recognizing a decision path adds no resolution implementation and no git or filesystem access inside the rule. Recognizing every `spx/`-prefixed decision-shaped string is excluded because it reports example and fixture paths; checking existence on disk is excluded because an untracked decision file exists in one working copy only, the same reason a link to it is broken.

Subprocess execution of the markdownlint-cli2 binary requires tool discovery, stdout parsing, and config-file management and is excluded. Writing `.markdownlint.jsonc` to validated directories produces side effects, risks git-status pollution, and requires cleanup, so `optionsOverride` owns configuration instead. An optional dependency with runtime discovery contradicts always-available validation with no skip path; a production dependency with a direct production binding satisfies that requirement.

## Verification

- ALWAYS: inside `spx/`, supply the product-owned link-shape rule through `customRules` in place of `markdownlint-rule-relative-links`; `docs/` keeps `markdownlint-rule-relative-links` with its product-root `root_path`
- ALWAYS: the product-owned rule resolves link existence and heading fragments by composing `markdownlint-rule-relative-links`' checks, presenting each tree-absolute `spx/` href to them as anchored at the product root
- ALWAYS: inside `spx/`, the product-owned rule reports a link with a `../` climb, a link with a leading-slash anchor, a relative link whose path enters a descendant node's directory, and a decision path written as text outside a link and outside fenced code blocks, naming the file, the line, and the offending link or path
- ALWAYS: the product-owned rule recognizes text as a decision path only when it begins `spx/`, ends in `.adr.md` or `.pdr.md`, and names a path in the tracked set supplied through its configuration; a decision filename without the `spx/` prefix, an `spx/` path absent from the tracked set, and any text when no tracked set is supplied are not reported
- NEVER: the product-owned rule stats, opens, or reads a link target on disk, or derives or matches heading-fragment slugs — its own verdict on a link target is tracked-set membership alone, and whether a target exists on disk and whether its heading fragment matches are decided only by the composed `markdownlint-rule-relative-links` checks
- ALWAYS: when the product root is a git repository, the step reads the paths git tracks under `spx/` once per validation run through `MarkdownValidationDeps` and supplies them, with the product root, through the product-owned rule's configuration; outside a git repository it supplies none, and the composed existence check alone decides whether a link resolves
- ALWAYS: given tracked paths, the product-owned rule resolves each admitted href to a product-relative path — a tree-absolute href from the product root, a node-local href from the citing file's directory — and reports a target inside the product root that git does not track as a broken link naming the file, the line, and the link, withholding it from the composed checks
- NEVER: the product-owned rule invokes git or reads the filesystem to decide tracked membership — the tracked set reaches it only through its rule configuration
- ALWAYS: accept the tracked-path listing through `MarkdownValidationDeps`, with the shared tracked-path reader over the default git runner wired only as the default dependency

### Audit

- ALWAYS: use markdownlint-cli2's `main()` function with `optionsOverride` for configuration — no config files written to disk ([audit])
- ALWAYS: accept the markdownlint `main()` entry point through `MarkdownValidationDeps`, with the imported production function wired only as the default dependency — enables isolated orchestration verification without replacing modules ([audit])
- ALWAYS: export `buildMarkdownlintConfig()` as a pure function returning the config object — enables isolated `l1` testing of rule selection ([audit])
- ALWAYS: export `getDefaultDirectories(productDir)` returning the default directories that exist under the product root — enables `l1` testing of directory discovery against fixture directories ([audit])
- ALWAYS: return structured error objects with file, line, and detail fields — enables programmatic consumption by the pipeline ([audit])
- ALWAYS: register markdown as a `ValidationLanguageDescriptor` composed through the validation registry per [spx/19-language-registration.adr.md](spx/19-language-registration.adr.md), ordered after the TypeScript language — pipeline ordering derives from the registry, not a hardcoded step index ([audit])
- NEVER: write config files to validated directories — produces side effects that pollute git status ([audit])
- NEVER: use subprocess execution for markdownlint — the programmatic API is available and preferred ([audit])
- NEVER: use `discoverTool()` or skip validation when markdownlint is unavailable — it is a production dependency, always present ([audit])
- NEVER: use `vi.mock()` or `jest.mock()` to replace markdownlint orchestration — inject a controlled `runMarkdownlint` implementation through `MarkdownValidationDeps` ([audit])
