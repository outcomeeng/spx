# Filename Grammar Ownership

The spec-tree library is the single canonical source of the versioned Spec-Tree filename grammar: every grammar token is declared exactly once in the library's `as const` registry surface, the grammar is an ordered set of self-contained naming-schema versions from which the product's methodology declaration selects the members a read accepts, and the library's recognizer classifies every filesystem name as valid, superseded, or invalid by retaining the names a read does not recognize — exposed through the shared multi-format reporter and depending on no downstream consumer at build or run time. This refines [`spx/23-spec-tree.enabler/21-kind-registry.adr.md`](21-kind-registry.adr.md), extending its single-source rule from kind vocabulary to the whole filename grammar.

The grammar carries a naming-schema version for the methodology lines spx reads — a 3.x version serving the 3.0, 3.1, and 3.2 lines and a 4.0 version serving the 4.0 line — ordered after the pre-3 version that carries the `.capability`, `.feature`, and `.story` node directories of the era before 3.0; each line's version encodes the statement `outcomeeng/methodology` makes authoritative for that line under its `AUTHORITY.md`, and no version serves a line no methodology version states. The 3.x grammar encodes `versions/3.0/` composed with the `versions/3.1/` and `versions/3.2/` deltas: `{index}-{slug}.enabler/` and `{index}-{slug}.outcome/` node directories each holding the spec `{slug}.md`, the root product file `{slug}.product.md` directly under `spx/`, the coordination notes `PLAN.md` and `ISSUES.md`, and an index of dot-separated digit runs (`versions/3.0/90-grammar.md`). The 4.0 grammar encodes `versions/4.0/methodology/product-tree/materialization/grammar.md`, `versions/4.0/methodology/product-tree/node/nodes.md`, and `versions/4.0/methodology/product-tree/product.md`: `{index}-{slug}{suffix}/` node directories whose suffix is one of `.product`, `.substrate`, `.capability`, `.domain`, `.interface`, `.surface`, and `.variant`, each holding the spec `{slug}.spec.md` that repeats its directory's slug; the root product spec `{name}.spec.md` directly under `spx/`, repeating the product's name, whose front matter declares `kind: product`; `ISSUES.md` as the only node-local note; and an index of a two-digit integer from `10` to `99` extended by two-digit fractional segments. Both grammars accept the decision form `{index}-{slug}.adr.md` and `{index}-{slug}.pdr.md` and the three test-file orderings `versions/3.1/README.md` introduced.

The product's methodology declaration selects the grammars a read accepts: a `methodology.version` on the 4.0 line selects the 4.0 grammar, a `methodology.version` on a 3.x line selects the 3.x grammar, and while `methodology.migratingFrom` names a 3.x line the 3.x grammar is selected beside the 4.0 grammar, so each name classifies by its own grammar and recognition and reading check no containment between a node of one selected grammar and a node of the other. A name a selected grammar accepts is valid; a name no selected grammar accepts but a naming-schema version ordered before the declared target's accepts is superseded, carrying the newest such version; every other name is invalid. A declaration naming a line for which the grammar carries no naming-schema version selects no grammar, and the read fails naming the declared version and the methodology lines spx reads. The selection reaches recognition through the `namingSchemaSelection` member of the `SpecTreeSource` that `createFilesystemSpecTreeSource({ productDir })` creates, which resolves that directory's methodology declaration, per [`spx/23-spec-tree.enabler/15-public-library-surface.adr.md`](15-public-library-surface.adr.md); `readSpecTree` takes no methodology input, so no reader call changes. A tree holds exactly one root product spec; a read finding more than one fails naming each, and a 4.0 root spec whose front matter does not declare `kind: product` fails the read naming that file.

## Rationale

Recognizing Spec-Tree filenames is a parsing concern, and the spec-tree library is the code that parses them. The methodology statement is the authority for what each line's grammar is — `AUTHORITY.md` places the declared version's statement above everything but itself — and the library is the executable encoding of that statement: it holds each line's forms once, hand-authored, so enforcement reads one source and spx depends on no artifact outside the product tree at build or run time.

The "exactly once" principle of [`spx/23-spec-tree.enabler/21-kind-registry.adr.md`](21-kind-registry.adr.md) reaches the whole grammar for the reason it governs kinds: a token declared in a consumer is drift invisible to the recognizer that owns the true vocabulary. Distinguishing superseded from invalid requires knowing prior grammars — a name is superseded exactly when an earlier schema version accepted it and no selected one does — so the grammar is an ordered set of complete schema versions rather than one current schema plus a hand-curated legacy list, which lets the recognizer report which version a name belongs to and derives the superseded set from real prior schemas. The recognizer already visits every name, so retaining the read's residual makes the invalid set the complement of recognition, with no second traversal and no separate scanner.

Selection follows the declaration because the declared version is the consumer's fact and the provider serves it: `AUTHORITY.md` makes an earlier version authoritative for a consumer that declares it even when a later one exists, and the product's agent capability lifecycle makes artifacts at the target and at the migration source both valid while a migration is open. Selecting both grammars only while `methodology.migratingFrom` names the source keeps a mixed tree governed during its migration and returns it to one grammar when the migration closes. Classifying each name by its own grammar, with no containment check across the two, follows from the same lifecycle: an artifact at either version resolves without failing on version shape alone, so a `.capability` under an `.enabler` is a valid state of a migrating tree. The 3.1 and 3.2 deltas leave node-directory, spec-file, and product-root naming unchanged, so every 3.x line selects the one 3.x version. Resolving the selection in the filesystem source keeps it with the adapter that reads the product directory, so every reader of a product tree receives it through the source it already passes. A name only a later grammar accepts is invalid rather than superseded, because supersession names a form a product has left, and a 3.2 product has not left a form it has not reached.

Rejected: treating the highest naming-schema version as canonical regardless of the declaration — once a 4.0 grammar exists it would classify every name of a product declaring 3.2 as superseded, overriding the version that product follows. Rejected: accepting every grammar for every product — a product declaring 4.0 alone would accrue 3.x forms with no migration declared, and no read would expose them. Rejected: reading the methodology statement at run time to recognize names — spx operates offline on the product tree, and a run-time read makes recognition depend on an artifact the product does not hold. Rejected: one current schema plus an ad hoc legacy-pattern list — it collapses all history into one undifferentiated bucket and cannot report which version a name conformed to. Rejected: generating the registry by codegen — a generated registry would make the grammar's single source the output of a second artifact the recognizer cannot see, while `as const` with `keyof typeof` provides typed vocabulary at compile time with no build step.

## Invariants

- Every Spec-Tree filename grammar token — kind and product suffixes, spec-file suffixes, evidence modes, execution levels, language tails, the runner token, segment and order separators, the order patterns, coordination-note names, and eval-lane names — is declared exactly once in the spec-tree library's `as const` registry surface.
- A read classifies the complete set of filesystem names beneath the tree: every name is exactly one of valid, superseded, or invalid, and invalid is the complement of the union of valid and superseded.
- The union of the selected grammars' accepted sets defines valid; the union of the accepted sets of the naming-schema versions ordered before the declared target's, less the valid set, defines superseded.
- The selected grammars are a function of the methodology declaration alone: the 4.0 line selects the 4.0 grammar, every 3.x line selects the 3.x grammar, and a `methodology.migratingFrom` on a 3.x line adds the 3.x grammar.
- A name's classification is a function of the selected grammars, the naming-schema versions, and the name with its enclosing path alone — independent of process environment, traversal order, and file contents.

## Verification

- ALWAYS: the grammar is an ordered set of self-contained naming-schema versions, each carrying its accepted filename forms, and the product's methodology declaration selects the members a read accepts
- ALWAYS: the 4.0 naming-schema version accepts the forms `versions/4.0/methodology/product-tree/materialization/grammar.md` states — node directories of the seven 4.0 kind suffixes, each holding `{slug}.spec.md`; the root `{name}.spec.md` directly under `spx/`; `ISSUES.md` as the only node-local note; and two-digit integer indices from `10` to `99` with two-digit fractional segments
- ALWAYS: the 3.x naming-schema version accepts the forms `versions/3.0/90-grammar.md` states as amended by `versions/3.1/README.md` and `versions/3.2/README.md` — `.enabler` and `.outcome` node directories, each holding `{slug}.md`; the root `{slug}.product.md` directly under `spx/`; `PLAN.md` and `ISSUES.md` as node-local notes; and dot-separated digit-run indices
- ALWAYS: a `methodology.version` on the 4.0 line selects the 4.0 grammar, a `methodology.version` on a 3.x line selects the 3.x grammar, and a `methodology.migratingFrom` on a 3.x line selects the 3.x grammar beside the 4.0 grammar
- ALWAYS: a name accepted by a selected grammar classifies valid; a name accepted by no selected grammar but by a naming-schema version ordered before the declared target's classifies superseded with the newest such version; every other name classifies invalid
- ALWAYS: a methodology declaration naming a line for which the grammar carries no naming-schema version fails the read naming the declared version and the methodology lines spx reads
- ALWAYS: a tree holding more than one root product spec fails the read naming each, and a 4.0 root spec whose front matter does not declare `kind: product` fails the read naming that file
- ALWAYS: recognition receives the declaration-selected naming-schema versions through the `namingSchemaSelection` member of `SpecTreeSource`, which the filesystem source created for a product directory resolves from that directory's methodology declaration; `readSpecTree` takes no methodology input and never resolves product configuration itself
- NEVER: determine a name's classification from the selected grammars alone — supersession requires consulting the naming-schema versions ordered before the declared target's
- NEVER: a read accepts a grammar the methodology declaration does not select
- NEVER: recognition or reading checks containment between a node of one selected grammar and a node of the other

### Audit

- ALWAYS: every Spec-Tree filename grammar token is declared once in the spec-tree library `as const` registry surface and consumed through the library surface ([audit])
- ALWAYS: the recognizer accepts the naming-schema versions, the selection the methodology declaration derives — the selected grammars and the declared target's naming-schema version — and a filesystem record as parameters and returns a classification of valid, superseded with its version, or invalid — so the classification is verified by injecting schema-version fixtures, with no mocking ([audit])
- ALWAYS: the reader retains every name the recognizer classifies as neither valid nor superseded and exposes that residual as the invalid set through the spec-tree snapshot ([audit])
- ALWAYS: grammar emission accepts the output format as a parameter and renders through the shared multi-format reporter ([audit])
- ALWAYS: the naming-schema versions are owned by the spec-tree library and exposed through its surface; downstream products obtain them by invoking spx ([audit])
- ALWAYS: recognizer and grammar tests inject schema-version fixtures constructed as local `as const` objects passed as parameters ([audit])
- NEVER: declare a Spec-Tree filename grammar token outside the spec-tree library registry surface ([audit])
- NEVER: read the methodology-documentation product, or any artifact outside the product tree, to recognize or classify a filename ([audit])
- NEVER: produce the grammar registry by codegen, build step, or runtime scanning — the grammar is hand-authored `as const` ([audit])
- NEVER: `vi.mock()`, `jest.mock()`, `memfs`, or any mocking mechanism for the recognizer or grammar — tests inject explicit schema-version fixtures and real filesystem records ([audit])
- NEVER: re-implement multi-format rendering for grammar emission instead of the shared reporter ([audit])
