# Host Command Lock

PROVIDES one host-wide slot that a guarded command holds for its whole process tree, admitted after a quiet load window and within a wait cap, and ended by one terminal result line
SO THAT agent sessions and automation across every repository, worktree, and session of one host
CAN take turns running heavy commands, each on a quiet machine, with no run released early by the death of its supervisor

## Assertions

- Given a free slot and a quiet load window, when a guarded command runs, then the lock file's directory is created before the file is opened, the slot is taken before the first sample, the holder record is written before the spawn naming the run id, the supervisor's process id, the working directory, and the start time with the child's process group unknown and is rewritten after the spawn with the child's process group, the child is spawned in a process group of its own with the locked descriptor at the reserved descriptor number and the lock environment exported, the binding never receives an unlock, and the run ends with `started: true`, `status: completed`, `childExitCode: 0`, and exit code 0 ([test](tests/admission.scenario.l1.test.ts))
- Given a slot held by another run, when a guarded command waits, then it retries after a base delay plus a randomized delay without starting, and starts only after the holder's child exits, so the two runs' intervals never overlap ([test](tests/admission.scenario.l1.test.ts))
- Given a guarded command whose child exits 3, when the run ends, then the result line reports `started: true`, `status: completed`, and `childExitCode: 3`, and the exit code is 3 ([test](tests/admission.scenario.l1.test.ts))
- Given a load source, a sleep, or a spawn that fails before the command runs, when the run ends, then the command never starts, the result line reports `lock_file_error` for the load source and the sleep and `spawn_failed` for the spawn, the exit code is nonzero, and the descriptor is released ([test](tests/admission.scenario.l1.test.ts))
- Given a held slot whose load window passes on its seventh sample after 30 seconds, when admission decides, then the command starts, and a window shorter than seven samples or 30 seconds never starts it ([test](tests/load-gate.scenario.l1.test.ts))
- Given a window in which a one-minute load exceeds 0.8 times the CPU count, a five-minute load exceeds the CPU count, a sample is invalid, two samples lie more than ten seconds apart, or the one-minute load rises across the window, when admission continues, then it discards the window and starts the command only after a fresh full window passes ([test](tests/load-gate.scenario.l1.test.ts))
- Given a slot taken while load is high, when admission decides, then it decides on a window sampled after the slot was taken, and samples taken before the slot was held never count ([test](tests/load-gate.scenario.l1.test.ts))
- Given a lock that stays busy until the wait cap, when the cap expires, then the command never starts, the result line reports `started: false` and `status: not_ready`, the exit code is 3, and nothing re-queues the command ([test](tests/wait-cap.scenario.l1.test.ts))
- Given a held slot whose wait cap expires during the load window, or between a passing window and the spawn, when the supervisor checks the cap, then the command never starts and the result line reports `not_ready` ([test](tests/wait-cap.scenario.l1.test.ts))
- Given a nested guarded call that carries a descriptor of the same orchestration lock file still holding the lock, when it runs, then its command starts at once in the inherited process group with no load window and no result line of its own, and the call keeps its command's exit code ([test](tests/nested.scenario.l1.test.ts))
- NEVER: a nested call whose descriptor is absent, changed, or no longer holds the lock starts its command; it fails `nested_context_invalid`, and a nested call resolving a different orchestration lock file fails `nested_lock_mismatch` ([test](tests/nested.compliance.l1.test.ts))
- Given a supervisor that stops after it records its child's process group, or after the child is spawned and before the process group is recorded, when another guarded command waits, then the waiter is admitted only after the child exits, and while it waits the holder record names the orphaned run's id, supervisor process id, working directory, and start time, with the child's process group in the first case and unknown in the second ([test](tests/supervisor-death.scenario.l1.test.ts))
- Given a supervisor that stops after it takes the lock and before it spawns its child, when another guarded command waits, then the waiter is admitted without waiting for any child ([test](tests/supervisor-death.scenario.l1.test.ts))
- Given a supervisor that stops before it reports, when the run's outcome is awaited, then no result line and no exit code exist, and the holder record is the only evidence naming the run ([test](tests/supervisor-death.scenario.l1.test.ts))
- The lock path maps: `SPX_ORCHESTRATION_LOCK_PATH` absolute → that path; `SPX_ORCHESTRATION_LOCK_PATH` empty or relative → failure before start; `SPX_ORCHESTRATION_LOCK_PATH` unset with `XDG_STATE_HOME` absolute → `$XDG_STATE_HOME/engineering.outcome/orchestration.lock`; both unset, or `XDG_STATE_HOME` relative → `$HOME/.local/state/engineering.outcome/orchestration.lock` ([test](tests/lock-path.mapping.l1.test.ts))
- The terminal result maps: a started child's exit code `n` → exit `n` with `childExitCode: n`; a child ended by signal `s` → exit 128 plus its number with `signal: s`; the wait cap → exit 3 with `status: not_ready`; invalid arguments, an unsupported platform, and a lock-file error → their own status and a nonzero exit before any start ([test](tests/terminal-result.mapping.l1.test.ts))
- NEVER: the guard starts its command on a platform other than macOS arm64, or through a lock file that fails to open, that another account owns, that is not a regular file, that lies on storage that is not local, or whose inode differs from the one it locked; each fails before start and no alternate path is tried ([test](tests/lock-file.compliance.l1.test.ts))
- Given a host that reports no positive logical CPU count, when a guarded command runs, then it fails before start with its own status and a nonzero exit, and the command never starts
- Given a child that leaves workers holding the inherited descriptor and exits, when another guarded command waits, then the waiter is admitted only after the last worker exits
- Given a running guarded command whose supervisor's process group receives SIGTERM and then SIGKILL, as a tool timeout or a stopped background task delivers them, or whose foreground process group receives SIGHUP, as a closed terminal pane delivers it, when each path runs, then a forwarded signal stops the guarded tree and releases the slot, and a supervisor SIGKILL leaves the tree holding the slot under its holder record until its last process exits
- Given a nested guarded call inside a guarded command whose inner command runs a worker, when the outer supervisor is interrupted, then every inner process stops, and no second outer guarded command starts while a worker that keeps its descriptor lives
- ALWAYS: missing lock directories are created with mode 0700 and the orchestration lock file with mode 0600, the lock file is opened without following a symbolic link, and the file is rewritten only in place and never unlinked, renamed, or replaced
- ALWAYS: the pinned binding loads from the installed package under Node 24 and takes, reports busy for, and releases at the last close a nonblocking exclusive lock that an inheriting child keeps after its parent closes its own copy
- NEVER: a code path releases the lock explicitly through the binding's unlock
