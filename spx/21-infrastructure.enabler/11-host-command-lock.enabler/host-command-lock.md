# Host Command Lock

PROVIDES one host-wide slot that a guarded command holds for its whole process tree, admitted after a quiet load window and within a wait cap, and ended by one terminal result line
SO THAT agent sessions and automation across every repository, worktree, and session of one host
CAN take turns running heavy commands, each on a quiet machine, with no run released early by the death of its supervisor

## Assertions

- Given two guarded commands started from two repositories that resolve the same orchestration lock file, when both run, then their run intervals never overlap ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a guarded command whose supervisor receives SIGKILL after it has recorded its child's process group, when another guarded command waits, then the waiter is admitted only after the child exits, and while it waits the orchestration lock file's holder record names the orphaned run's id, supervisor process id, child process group, working directory, and start time ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a supervisor killed after it spawns its child and before it records the child's process group, when another guarded command waits, then the waiter is admitted only after the child exits, and the holder record names the run with its child process group unknown ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a supervisor killed after it takes the lock and before it spawns its child, when another guarded command waits, then the waiter is admitted without waiting for any child ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a child that leaves workers holding the inherited descriptor and exits, when another guarded command waits, then the waiter is admitted only after the last worker exits ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a running guarded command whose supervisor's process group receives SIGTERM and then SIGKILL, as a tool timeout or a stopped background task delivers them, or whose foreground process group receives SIGHUP, as a closed terminal pane delivers it, when each path runs, then a forwarded signal stops the guarded tree and releases the slot, and a supervisor SIGKILL leaves the tree holding the slot under its holder record until its last process exits ([test](tests/kill-paths.scenario.l2.test.ts))
- The signals each harness kill path delivers to a running guarded command (the tool timeout, the stopped background task, and the closed terminal pane) are observed on the host and recorded ([probe](probes/harness-kill-paths/probe.md))
- Given each supported real chain on macOS arm64 (a guarded `vitest` run, a guarded shell script that runs its workers in the foreground, a guarded `just` recipe, and a guarded `pytest -n 2` run), when it completes normally, then the slot stays held from admission until the run's last process exits ([test](tests/launch-chains.scenario.l3.test.ts))
- Given each supported real chain on macOS arm64, when its supervisor receives SIGKILL while its workers run, then a competing guarded command attempted while a worker is observed alive and active through its own activity signal, not through descriptor possession, is not admitted, and it is admitted only after the last worker exits ([test](tests/launch-chains.scenario.l3.test.ts))
- Given each supported real chain on macOS arm64, when the runner's main process dies while its workers survive, then a competing guarded command attempted while a worker is observed alive and active through its own activity signal is not admitted, and it is admitted only after the last worker exits ([test](tests/launch-chains.scenario.l3.test.ts))
- Given each supported real chain on macOS arm64, when the supervisor and every wrapper process between it and the workers are gone while workers remain, then a competing guarded command attempted while a worker is observed alive and active through its own activity signal is not admitted, no surviving wrapper process holds the slot, and it is admitted only after the last worker exits ([test](tests/launch-chains.scenario.l3.test.ts))
- Given a nested guarded call inside a guarded command whose inner command runs a worker, when the outer supervisor is interrupted, then every inner process stops, and no second outer guarded command starts while a worker that keeps its descriptor lives ([test](tests/nested.scenario.l2.test.ts))
- Given a nested guarded call that carries a descriptor of the same orchestration lock file still holding the lock, when it runs, then its command starts at once in the inherited process group with no load window and no result line of its own ([test](tests/nested.scenario.l2.test.ts))
- Given a guarded command whose child exits 3, when the run ends, then the result line reports `started: true`, `status: completed`, and `childExitCode: 3`, and the exit code is 3 ([test](tests/host-command-lock.scenario.l2.test.ts))
- Given a held slot whose load window passes on its seventh sample after 30 seconds, when admission decides, then the command starts, and a window shorter than seven samples or 30 seconds never starts it ([test](tests/load-gate.scenario.l1.test.ts))
- Given a window in which a sample exceeds a limit, a sample is invalid, or two samples lie more than ten seconds apart, when admission continues, then it discards the window and starts the command only after a fresh full window passes ([test](tests/load-gate.scenario.l1.test.ts))
- Given a slot taken while load is high, when admission decides, then it decides on a window sampled after the slot was taken, and samples taken before the slot was held never count ([test](tests/load-gate.scenario.l1.test.ts))
- Given a lock that stays busy until the wait cap, when the cap expires, then the command never starts, the result line reports `started: false` and `status: not_ready`, the exit code is 3, and nothing re-queues the command ([test](tests/wait-cap.scenario.l1.test.ts))
- Given a held slot whose wait cap expires during the load window, or between a passing window and the spawn, when the supervisor checks the cap, then the command never starts and the result line reports `not_ready` ([test](tests/wait-cap.scenario.l1.test.ts))
- The lock path maps: `SPX_ORCHESTRATION_LOCK_PATH` absolute → that path; `SPX_ORCHESTRATION_LOCK_PATH` empty or relative → failure before start; `SPX_ORCHESTRATION_LOCK_PATH` unset with `XDG_STATE_HOME` absolute → `$XDG_STATE_HOME/engineering.outcome/orchestration.lock`; both unset, or `XDG_STATE_HOME` relative → `$HOME/.local/state/engineering.outcome/orchestration.lock` ([test](tests/lock-path.mapping.l1.test.ts))
- The terminal result maps: a started child's exit code `n` → exit `n` with `childExitCode: n`; a child ended by signal `s` → exit 128 plus its number with `signal: s`; the wait cap → exit 3 with `status: not_ready`; invalid arguments, an unsupported platform, and a lock-file error → their own status and a nonzero exit before any start ([test](tests/terminal-result.mapping.l1.test.ts))
- For every series of load samples and every logical CPU count, a window admits exactly when it holds at least seven samples spanning at least 30 seconds with no gap over ten seconds, every one-minute load is at most 0.8 times the CPU count, every five-minute load is at most the CPU count, and the fitted one-minute rise is at most 0.05 times the CPU count ([test](tests/load-gate.property.l1.test.ts))
- NEVER: a nested call whose descriptor is absent, changed, or no longer holds the lock starts its command; it fails `nested_context_invalid`, and a nested call resolving a different orchestration lock file fails `nested_lock_mismatch` ([test](tests/nested.compliance.l2.test.ts))
- NEVER: the guard starts its command on a platform other than macOS arm64, or through a lock path that is a symbolic link, a lock file another account owns, or a lock file whose inode differs from the one it locked; each fails before start and no alternate path is tried ([test](tests/lock-file.compliance.l2.test.ts))
- ALWAYS: missing lock directories are created with mode 0700 and the orchestration lock file with mode 0600, and the file is rewritten only in place and never unlinked, renamed, or replaced ([test](tests/lock-file.compliance.l2.test.ts))
- ALWAYS: the pinned binding loads from the installed package under Node 24 and takes, reports busy for, and releases at the last close a nonblocking exclusive lock that an inheriting child keeps after its parent closes its own copy ([test](tests/binding.scenario.l2.test.ts))
- NEVER: a code path releases the lock explicitly through the binding's unlock ([audit])
