# Test Execution Recording and Per-Node Run

Last-run evidence recording and the registry-based per-node run are command-layer handlers under `src/commands/test/` that share one recording path: each resolves the discovered test files for its scope, dispatches the matching files through the testing registry, assembles a `TestRunState`, and persists it through the injected `TestRunStateFileSystem`. The four staleness digests are derived by one shared current-staleness-inputs function that both the recording path and the status resolver's freshness check consume, so a node's recorded staleness inputs and the current inputs later compared against them derive from one recipe. This decision composes only that parent surface; the storage schema, atomic write, digest derivation, and staleness comparison are governed by [`spx/41-test.enabler/43-last-run-evidence.enabler/11-last-run-file.adr.md`](spx/41-test.enabler/43-last-run-evidence.enabler/11-last-run-file.adr.md), [`spx/41-test.enabler/43-last-run-evidence.enabler/21-test-state-storage.adr.md`](spx/41-test.enabler/43-last-run-evidence.enabler/21-test-state-storage.adr.md), [`spx/41-test.enabler/43-last-run-evidence.enabler/32-terminal-write-protocol.adr.md`](spx/41-test.enabler/43-last-run-evidence.enabler/32-terminal-write-protocol.adr.md), and [`spx/41-test.enabler/43-last-run-evidence.enabler/43-staleness-comparison.adr.md`](spx/41-test.enabler/43-last-run-evidence.enabler/43-staleness-comparison.adr.md). The four staleness inputs are derived from sources outside this node: the testing config digest from the canonical descriptor digest (`spx/16-config.enabler/54-canonical-descriptor-digest.enabler/canonical-descriptor-digest.md`), the product input digests from root paths declared by the testing language descriptors and covered-test-path-derived inputs those descriptors derive, and the discovered path-set and content digests from the child helpers `digestTestPaths` and `digestTestContents`; the branch name and head SHA are recorded identity fields, not staleness inputs, sourced from the product-directory API (`spx/16-config.enabler/65-product-directory-api.enabler/product-directory-api.md`).

Before dispatch, the recording path consults the recorded runs for one that already satisfies the request, as governed by [`spx/41-test.enabler/13-evidence-reuse.pdr.md`](spx/41-test.enabler/13-evidence-reuse.pdr.md). The files a request selects resolve through one selection function under `src/commands/test/`, which the reuse lookup and the dispatch both consume. The lookup considers only the latest terminal run that covers every selected file, ordered as the per-node selection of the last-run evidence orders runs, and compares that run's recorded staleness inputs with the current inputs the shared current-staleness-inputs function derives over the run's own covered set. A run satisfies the request only when its head commit equals the current head commit, git identity resolves for both, the recorded verdict of every selected file is `passed`, and the worktree holds no staged, unstaged, or untracked git-visible change. A satisfied request returns a result kind distinct from an executed run, carrying the reused run's file coordinates and its outcomes restricted to the selected files, and no run file is reserved or written for it.

## Rationale

A single recording function consumed by both runs guarantees the two produce identical evidence shape and staleness inputs — a node refreshed individually is indistinguishable from the same node covered by a full run, which is what lets status read either interchangeably. Placing recording in `src/commands/test/` follows the layering in [`spx/14-cli-composition.adr.md`](spx/14-cli-composition.adr.md): it composes the pure digest helpers and the storage surface with filesystem, clock, and git reads, returns a result, and carries no Commander binding or process exit, so it verifies against temporary fixtures. Dispatching the per-node run through `src/test/registry.ts` keeps the single-node path language-agnostic per [`spx/19-language-registration.adr.md`](spx/19-language-registration.adr.md), so the status domain obtains every outcome through one registry-driven path and names no language. Returning the per-node outcome to the caller — rather than having the testing domain reach into status — preserves the composition direction declared by [`spx/31-spec-domain.enabler/54-spec-cli-commands.enabler/21-status-testing-delegation.adr.md`](spx/31-spec-domain.enabler/54-spec-cli-commands.enabler/21-status-testing-delegation.adr.md): status composes the testing provider through an injected resolver, and the testing domain depends on neither the status nor the spec domain.

Recording inside the pure dispatch (`runTests`) or the testing domain layer was rejected because it drags filesystem, clock, and git I/O into a layer [`spx/14-cli-composition.adr.md`](spx/14-cli-composition.adr.md) keeps free of them; recording inside the Commander descriptor was rejected because it mixes evidence assembly with the process boundary, exercisable only through the built executable; separate recording paths for the full run and the per-node run were rejected because they let the two drift in captured fields or digest derivation, breaking the read-either-interchangeably property; a status-owned per-node runner was rejected because it duplicates registry dispatch and forces status to name languages.

Reuse resolves its selection and its currency inputs through the same functions the dispatch and the status resolver consume, so a lookup and a dispatch address one file set and a recorded run is never judged by a recipe that differs from the one that recorded it. The lookup evaluates only the latest covering terminal run, so an older passed run never stands in for a later failed or stale run over the same files. A passed run covering a superset of the selection satisfies it, because the comparison runs over the candidate's own covered set. The four staleness digests reach no source file a test imports, so reuse additionally requires an unchanged head commit and a worktree without a git-visible change; a verdict the runner's report omitted is incomplete evidence and never satisfies a request. A reuse writes no run file because each run file records one execution, so the latest covering run that status reads is unchanged by a reuse. The per-node run that serves the status resolver never consults a recorded run, because status must observe an execution of the node.

Reuse inside the journaled verification run was rejected because the sealed journal records executions that CI reproduces. A lookup with its own selection logic was rejected because it lets the lookup and the dispatch address different file sets.

## Invariants

- The full-suite recording and the per-node recording assemble and persist their `TestRunState` through one shared recording function; the scopes differ only by the discovered-file subset they cover.
- A node's recorded staleness inputs and the current staleness inputs the status resolver compares against them are derived by one shared current-staleness-inputs function; the record side and the read side never derive the four digests by separate recipes.
- Every persisted `TestRunState` carries runner outcomes, the four staleness digests (config, path-set, content, product-input), and the branch and head-SHA identity fields.
- The per-node run's result is the node's runner outcome returned to the caller; the testing domain imports neither the status nor the spec domain.
- A request that a recorded run satisfies returns that run's outcomes restricted to the selected files in a result kind distinct from an executed run, and writes no run file.
- The reuse lookup and the dispatch resolve the selected files through one selection function.

## Verification

### Testing

- ALWAYS: the reuse lookup considers only the latest terminal run that covers every selected file, ordered as the per-node selection of the last-run evidence orders runs, so an older passed run never stands in for a later failed or stale run that covers the same files ([compliance])
- ALWAYS: the candidate's recorded staleness inputs compare with the current inputs the shared current-staleness-inputs function derives over the candidate's own covered set, so a passed run that covers a superset of the selection satisfies it ([property])
- ALWAYS: the candidate satisfies the request only when its head commit equals the current head commit, git identity resolves for both, the recorded verdict of every selected file is `passed` because a file the runner's report omitted is incomplete evidence, and the worktree holds no staged, unstaged, or untracked git-visible change ([mapping])
- ALWAYS: a satisfied request returns a result kind distinct from an executed run, carrying the reused run's file coordinates and its outcomes restricted to the selected files, and the command descriptor reports it ([compliance])
- NEVER: reserve or write a run file for a result taken from a recorded run ([compliance])
- ALWAYS: a request that requires execution skips the lookup ([compliance])

### Audit

- ALWAYS: the recording path resolves the selection's current staleness inputs through the shared current-staleness-inputs function before dispatch, and returns the satisfying recorded run in place of dispatching, with no run file written, when one exists ([audit])
- ALWAYS: the files a request selects — discovery, operand targeting, and the passing scope — resolve through one selection function under `src/commands/test/` that the reuse lookup and the dispatch both consume, so a lookup and a dispatch address one file set ([audit])
- NEVER: the per-node run that serves the status resolver consults a recorded run ([audit])

- ALWAYS: evidence recording and the per-node run live under `src/commands/test/` as handlers that return results and accept filesystem, clock, and git access as injected parameters — so they verify against temporary fixtures without mocking ([audit])
- ALWAYS: the full-suite run and the per-node run assemble and persist their `TestRunState` through one shared recording function — so per-node and full-run evidence are identical in shape and staleness inputs ([audit])
- ALWAYS: the per-node run dispatches through `src/test/registry.ts` and selects the node's tests by its discovered test paths — so the single-node path names no language ([audit])
- ALWAYS: the recording handler derives all four staleness digests (testing config digest, discovered path-set digest, discovered content digest, testing-language product input digests from root and covered-path-derived inputs) and records the branch name and head SHA, persisting through the injected `TestRunStateFileSystem` ([audit])
- ALWAYS: derive the four staleness digests through one shared current-staleness-inputs function that the recording path and the status resolver's freshness check both consume — so freshly recorded evidence is never read as stale through recipe drift ([audit])
- ALWAYS: the per-node run returns the node's runner outcome to its caller for the injected status resolver to consume ([audit])
- NEVER: place evidence recording or per-node run orchestration in `src/domains/test/` or in the Commander descriptor — I/O orchestration belongs to the command layer ([audit])
- NEVER: reference a specific language by name in the per-node run dispatch — every outcome arrives through the registry enumeration ([audit])
- NEVER: access the filesystem, clock, or git through direct `fs`, `Date.now`, or `child_process` calls instead of injected dependencies, or stand in a double via `vi.mock()` / `jest.mock()` ([audit])
- NEVER: the testing domain imports the status or spec domain — the per-node outcome flows outward through the returned result, never through a reverse import ([audit])
